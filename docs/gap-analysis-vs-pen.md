# 差距复盘：OpenDesigner 与 pen.dev 的功能/效果对照

> 记录时间：2026-11-10
> 触发：用户反馈「和 pen.dev 功能完全比不上，效果也比不上」
> 依据：本文所有关于 pen.dev 的事实**均来自本仓库 `docs/research.md`**（竞品拆解报告，2026-10-31 实测），
> 不引入新的二手信息。所有关于本项目的陈述均可用仓库内命令复核。
> 性质：**决策记录（ADR）**。不修改 research.md 的既有结论，本文件是增量。

---

## 1. 一句话结论

**我把预算全部花在「最难但看不见」的地方，做完了技术前提，却没盖任何一间用户能走进去的房子。**

Phase 0（摸引擎语义，154 字段）+ Phase 1（od-format 序列化层，305 测试）都是必要的，
但它们产出的是**库**，不是**用户能用的东西**。
到 Phase 1 结束，用户手上是：一个能无损存文档的格式层 + 一条 `od convert` 命令。
拿这个去和 pen.dev 的「打开就能画、agent 直接改稿、一键出代码」比，**当然比不上**。

这不是能力问题，是**优先级判断错误**。

---

## 2. 我做错的三件事

### 2.1 把「技术命门」当成了「交付物」

`research.md` §5.1 第 4 条原文：

> 引擎文档模型 → 文本 JSON 的**序列化保真度**是整个差异层的技术命门（组件 + 自动布局 + 变量
> 三者 round-trip 无损才算成立），必须先实测再立项。

我读成了「先做命门」。**命门是前提，不是交付物。**
前提做完就该立刻往上盖产品面；我把"前提"当终点交付了整整两轮。

### 2.2 交付物形态选错了

我交付的是「包 + 305 个测试 + 一份规格文档」。
用户不会 `npm install` 一个包然后去读 305 个测试来获得价值。

pen.dev 的第一眼体验是：**打开 → 画 → 复制出代码 → agent 改稿**。
我的第一眼体验是：**读一份 2816 行的规格**。
交付物的**形态**就不对——不是内容不够好，是用户拿到手不知道该拿它干什么。

### 2.3 验收标准选错了维度

Phase 1 的验收标准是「往返无损」。这是**内部正确性**，不是**用户价值**。

`research.md` §6.4 的 P0 验收标准原文是：

> 一个 `.json` 设计文件能被读写往返；v1→v2 迁移有测试覆盖；引擎可在 Node 里 headless 运行

我按字面做完了，三条都过了。但这条标准本身有个盲区：
它**从头到尾没提「用户拿这个文件去干什么」**。

我在 §6.4 漏读的那一层是 §6.2 的 MVP 必做项表：
**Agent（MCP server）/ 导出（HTML+CSS/Tailwind）/ 导入** 才是用户可感知的那部分。

### 3.1 这张表说明什么

- **「已对齐」的部分**（格式、组件、变量、布局）**全是看不见的部分**。
- **「比不上」的部分**（agent 入口、出代码、截图、多端、协作）**全是看得见的部分**。
- 所以差距感不是错觉，是**结构性的**：我把工程正确性做到了 A，把产品可见性留在了 F。

## 4. 本轮（Phase 2）在补什么

三块并行 + 一轮验收：

| 模块 | 是什么 | 对应 pen.dev 的什么 |
|---|---|---|
| `packages/od-ops` | 面向 agent 的操作 DSL：insert/update/delete/move/set/reorder/batch，**原子性 + 全量校验** | §3.3 的 `execute` DSL（**pen.dev 最值得学的抽象**） |
| `packages/od-mcp` | MCP server（stdio），5 个工具：read_doc / list_nodes / apply_ops / screenshot / export | §6.2 MVP 必做项原文清单 |
| `packages/od-cli` 的 export/apply/mcp | `od export --to svg\|html\|tailwind\|jsx\|png\|pdf`、`od apply`、`od mcp` | §2.8 导入导出 + §2.7 CLI |
| `scripts/gen-templates.ts` | 中文社媒尺寸模板 + 一键多尺寸派生 | §5.1 第 2 条「中文内容创作工作流」 |

### 4.1 关键认知修正

**引擎（`@open-pencil/core`）里本来就有全套导出能力**：`renderNodesToSVG` / `headlessRenderNodes` /
`htmlFormat` / `tailwindJSXFormat` / `jsxFormat` / `pdfFormat`，实测全部可用。

也就是说：**「设计→代码 + 截图」这件事的成本几乎是零，是我没接。**
Phase 1 我把 core 当成"渲染后端，CLI 用不上"，于是只用了它的图模型。
这个判断本身就错了——**core 才是产品的效果层，不是负担**。

## 5. 明确不追的（不是"做不了"，是"不该做"）

引 `research.md` §6.4「明确不做」与 §4.2「不利于开源友好」：

- 自研 WebGL 渲染管线、GLSL shader 节点、mesh 渐变
- Script 节点（Code on Canvas）、浏览器节点
- `.fig` 闭源格式解析（法务风险）
- 托管模型、模型配额、云分享快照、账号体系
- 兼容 `.pen`（上游保留破坏性变更权，且洁净室红线不允许抄字段名）

**pen.dev 的"重"正是它的负担来源**（§4.1 五端并行、渲染野心、功能面爆炸、
编排层复杂度、云端依赖、导入复杂度被低估、打包门槛、配额仪式感、两端体验割裂）。
我们要赢的点是 §6.1 的三条硬承诺：**格式不破坏 / 不设配额 / 一个核心四种壳**，
外加 §5.1 第 2 条的**中文内容创作工作流**。

## 6. 做完 Phase 2 之后，剩下的差距（诚实清单）

| 差距 | 严重度 | 计划 |

| 没有图形编辑器 UI（只能命令行 + agent 改稿） | 高 | Phase 3：接 `@open-pencil/vue` 做中文 Shell |

## 7. 我给自己立的规矩（写下来防止重犯）

1. **每个阶段必须有一条命令能让用户立刻看到东西**。做不到 = 这个阶段不算完成。
2. **验收标准里必须有一条是"用户视角"的**，不是"内部一致性"的。
3. **引擎已有能力优先复用，不要自己造**。core 里已经有一整套导出器。
4. **每轮结束问一次"用户拿这个能干什么"**，答不上来就是白做。
5. 交付前跑一次**从零 clone 的端到端演示**（`scripts/phase2-demo.ts`），
   而不只是跑单元测试。
